# Release 0.8.0 — Request Details and Member Withdrawals

Baseline: v0.7.3.

- Management Issue Requests shows member name, designation/unit, email and optional mobile on separate lines. Designation is eager-loaded with the member to avoid per-row queries.
- Member Requests uses separate blue request and green loan panels, distinct table headings/text, timestamps, and spaced pagination summaries. Approved requests show the actual linked loan issue timestamp.
- A Library Member can withdraw only their own pending request, before approval/rejection. Withdrawal keeps the record and stores `withdrawn_at`; no loan is created, no issue count is changed. The member can submit a new request later, subject to the normal stock/duplicate checks.
- Withdrawal and approval acquire the book/request locks in the same order, then recheck status under the request lock. Approval cannot act on a withdrawn request, and withdrawal cannot act on an approved request. Repeated withdrawal and cross-member access are rejected server-side.
- Administrators/Librarians (and existing authorized Library Staff) see requested/withdrawn timestamps, withdrawn status and actual issue dates. Withdrawal is audited as `book.issue_request_withdrawn`, with member/book IDs and timestamp; the existing request submission audit remains in place.

## Apply

Back up the project/database, extract this root-relative ZIP over v0.7.3, then run:

```bat
php artisan optimize:clear
php artisan migrate --force
php artisan test
```

The new migration adds one nullable withdrawal timestamp. README, existing migrations and compiled assets are unchanged. No Composer/npm update or asset rebuild is required; member page styles are scoped through the existing layout style stack.

## Validation

Added five regression tests for ownership, pending-only withdrawal, repeated requests, approval/withdrawal order, audit/stock preservation, issue dates and management member details.
